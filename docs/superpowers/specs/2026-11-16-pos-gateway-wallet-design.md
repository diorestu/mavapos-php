# POS Midtrans gateway and merchant wallet

User decisions: gateway for new POS checkout only; owner wallet balance and manual withdrawal requests processed by platform admin (superadmin). One existing shared Midtrans account remains; wallet is an internal merchant/environment ledger, not a separate Midtrans bank balance.

## Scope and invariants
- Keep subscription billing separate. Only persisted POS gateway payment records can credit merchant wallets. Tenant and originating outlet are captured server-side, never inferred from the shared balance or notification-supplied tenant fields.
- Pending POS gateway sales reserve stock and remain outside active sales/omzet, customer metrics, bonus and exports. Ordinary existing sales default to paid. Verified capture/settlement pays the sale; wallet credit waits for settlement. Terminal failed/expired unpaid sales restore stock once. The original cashier shift is retained even if later closed.
- Gateway is online-only, direct and single-method. Initial version rejects offline replay, split, complimentary and loyalty redemption/stamping for gateway; other existing methods retain those features. Normal discounts are supported. Server totals remain authoritative.
- Dedicated UUID checkout request plus canonical payload hash prevents duplicate sales/charges; remote creation happens after committing the reservation. Concurrent/repeated requests reuse the same payment or return a retryable creation state, never create a second charge silently.
- Midtrans status is fetched using server credentials after signature verification. Stable gateway order IDs route notification to POS versus subscription. Gross amount/currency/environment/transaction identity must match. Browser callbacks never grant payment.
- Sandbox/live ledger isolation. Integer IDR only. Immutable ledger postings uniquely keyed per account/event, under account/payment row locks; duplicate and out-of-order notifications do not duplicate money.
- Wallet buckets: unreconciled gateway funds, available net funds, reserved withdrawals, paid out, fees. Gross settlement goes to unreconciled. Superadmin records actual verified Midtrans fee (zero allowed with confirmation/reference); move remaining gross minus known refunds minus fee to available. Unknown fees are not treated as zero or withdrawable.
- Cumulative remote refunds/chargebacks debit the correct bucket exactly once. Local manual refunds are blocked for gateway sales to avoid recording a bank refund without the gateway movement. External refund reversals do not automatically restock goods; gateway financial adjustment is visible separately. Paid gateway sales cannot be edited/voided/transferred by legacy tools.
- Owner can request withdrawal against available net balance with bank details and a stable request UUID. Reserve immediately; no overspending or duplicate requests. Superadmin may start processing (coverage check), reject (release), or mark transferred with actual bank reference/confirmation. Completed payouts record manual transfers; no bank transfer API is called. Negative wallet liability after a later refund remains visible and prevents new withdrawals.
- Wallet and ledger views enforce owner isolation; outlet/date filters affect listings and displayed outlet balances explicitly. Wallet-wide requests use merchant-wide available funds. Superadmin review spans merchants with filters. No cross-merchant IDs may be accepted from owner actions.
- Scheduled reconciliation handles missed notifications and unused expired Snap pages. Pending gateway sessions can be reopened from the sales list. Shift deletion and account SQL import cannot erase financial gateway history silently.

## Delivery and validation
Reuse the existing Midtrans client and Snap.js pattern, with a dedicated POS gateway service/controller and ledger/payout service. Introduce gateway_payments, wallet_accounts, wallet_entries, wallet_withdrawals, and paid/pending status on pos_sales. Add POS method, pending gateway page, merchant wallet and superadmin review screens in existing Blade styling.

Test provider/tenant isolation, checkout idempotency and stock reservation/release, settlement versus capture, duplicate/out-of-order refunds, fee reconciliation, withdrawal reservation/transitions, auth and subscription-expiry access to existing funds, pending-sales report exclusion, and existing POS/offline/subscription regressions. UI browser checks and full suites/build before completion. No production migration, real payouts or live charge submission during implementation.
