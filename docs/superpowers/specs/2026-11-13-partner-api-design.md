# Partner REST API v1

Provide read-only merchant-scoped outlet, product, transaction and sales-summary JSON under `/api/partner/v1`. Dedicated hashed bearer keys are independent of Sanctum, so they cannot authorize POS mutations. Operator commands issue/revoke live or sandbox keys; owner/admin settings endpoints manage these same keys. All outlets of the key's merchant are accessible, never another merchant's data. Explicit tenant predicates apply even outside interactive authentication.

Transactions require outlet_id, from and to (ISO8601 with timezone, half-open [from,to), maximum 31 days), including voids and refunds by default. Pagination is bounded to 100; deterministic sold_at/id ordering. updated_since additionally considers refunds, so callers can poll changes to older sales by choosing the original sale window. Integer IDR, UTC storage and Asia/Makassar (+08:00) response timestamps. Item name/SKU/quantity/prices come from captured sale rows. Existing records lack historical modifier/variant attributes and per-line allocations of order discounts; expose this honestly as null, not fabricated values. Capture variant name/attributes on all new sale items with a nullable variant_snapshot column; no backfill from mutable catalog. Summary excludes voids; refunds are attributed to original sale window and shown separately.

60 requests/minute/key shared across endpoints. Sandbox key only accesses `/api/partner/sandbox/v1` and deterministic fixtures using the same serializers and validation; no writes to real sales or outward requests. Production keys cannot read sandbox and vice versa. Do not invent a subscription plan/fee; read-only integration is gated by key validity and current owner role, independent of POS subscription expiry to allow reconciliation.

Optional `transaction.created` webhooks: one endpoint/key, authenticated registration, encrypted signing secret, persistent delivery outbox inserted with sale creation inside checkout's transaction; no HTTP during checkout. Signed minimal event references the sale for GET detail. Scheduled sender retries 5 attempts, uses stable event ID and HMAC timestamp/body, disables redirects and pins public HTTPS destination DNS to prevent internal network requests. Explicit operator hostname allowlist. Revocation disables queued sends. Sandbox offers synthetic test delivery payload/signature, with no actual HTTP. Existing sales do not emit retroactive events.

Approach: separate partner credentials and controllers rather than extending mobile controllers or broad Sanctum permissions. A database outbox with scheduler is chosen over synchronous requests or a second queue dependency. Sandbox is a contract fixture service, not a cloned customer database.

Verification: isolation, read-only credentials, expiry/revocation, precise date boundaries, missing historical fields, refund/void and split payment behavior, sandbox separation, pagination/429, webhook ownership, signing/retry/rollback, existing checkout/export regressions. No production deployment or real credentials are created automatically.
