# POS reliability and partial refunds

User requested implementation of the first three gaps: offline transactions, duplicate checkout protection, partial returns/refunds. Existing Laravel/Alpine POS and branch/tenant rules remain authoritative.

## Decisions
- Existing checkout gains optional Idempotency-Key (also client_transaction_id body) scoped to tenant, bound to authenticated actor/branch and canonical payload. Successful JSON is replayed; reused key with changed context/data returns 409. Failures are retryable. Server-side transaction/locking ensures exactly one stock/payment/loyalty mutation.
- Browser uses durable IndexedDB outbox scoped to login user, active cashier, branch and shift. Client generates a stable UUID before first submission and persists before sending. Only network failures become pending; HTTP errors stay visible. Unknown responses never get a new ID. Retry is sequential, auth-expired pauses, validation conflicts remain pending with errors. No automatic cross-user or cross-branch submission or queue deletion on logout.
- Offline is a continued already-open POS session; cache an offline-capable shell after an online visit, not arbitrary authenticated HTML. Cache scope is user+branch, clear/mismatch protection on identity changes. Offline checkout supports direct cash/QRIS/card/split manually recorded payments. Online merchant and loyalty/redemption require connectivity. Pending receipts explicitly say unsynchronized and use local UUID, not a fabricated server invoice.
- Offline sync includes original cashier_shift_id, offline_created_at and expected_total. Server validates branch/actor/shift, captured time within shift and past, expected amount/stock; rejects conflicts without changing inventory or dropping queue. Same user can sync after closing original shift; server recomputes that shift. Return online catalog/session on success.
- Partial refunds: owner/admin only, same tenant/active branch, original item IDs and quantities, reason required. Cashier cannot refund. Refunds are immutable linked documents, not editing/deleting original sales. Net refundable amount allocated from original discounted total with cumulative integer rounding so multiple returns never exceed the original paid sale; merchant cap uses original net receipt. Each request has a unique idempotency key. Refunded qty cannot exceed sold qty. Returned stock only when explicitly selected; recipe consumables are not restored automatically. No refunds on voided sales, no void/edit/branch-transfer after any refund. Refunds record actual manual refund method; no external transfer is claimed.
- Expose refund action/history from sales. Add refund reporting separately from gross sales with date/branch filters and net-after-refunds summaries; shift cash balances subtract cash refunds attributed to the processing shift where possible. Original sales and sales bonuses are preserved (bonus reversals require a separate explicit business rule).
- No production database mutation, push, commit or deployment is authorized by this implementation request.

## Verification
Feature tests for duplicate replay/context conflicts/retry, offline original shift/time/quote validation and retained outbox errors, partial quantities/rounding/concurrency/authorization/stock/merchant limits. Node tests for outbox retry identity/network error semantics. Build and full PHP suite; inspect rendered refund flow and offline queue where tools permit.
